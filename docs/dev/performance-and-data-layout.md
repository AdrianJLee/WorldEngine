# 数据布局与性能标准 (v1)

> 面向**改引擎的人**与**后续接入开发的 AI**。
> 本文是可执行的工程规范与门禁判据，不是理论散文。
> 所有规则附带明确的**证据义务**（要写什么编译期断言、跑什么测试门禁、提供什么基准数字）。

---

## 4.0 谁读、什么时候读

任何改动满足下列任一条**之前**，先读完本文并执行 §4.1 的判定四问：

- 新增或修改**组件**（`Component`）、`schema` 字段、`entt` 池内数据结构；
- 新增或修改**跨边界结构体**：宿主 ↔ `WorldRuntime.dll`、插件 ABI、GPU 侧 UBO / 顶点 / 实例缓冲、二进制资产头、Lua usertype；
- 新增或修改**每帧遍历**的容器或**热路径**数据结构；
- 试图编写 `alignas` / `#pragma pack` / 手写填充字节（padding）/ 结构体数组（AoS）转数组结构体（SoA）拆分 / AVX / SIMD 内建函数。

---

## 4.1 判定四问（先判“需不需要”，再判“怎么做”）

在动手改动内存布局或引入优化之前，必须按顺序回答以下四个问题：

| 问 | 判据 | 答 "No" 的后果 |
| --- | --- | --- |
| **Q1 热吗？** | 该数据每帧被遍历的实例数 `≥ 1000`，**或**已有实测剖析（profiling）证据表明其占单帧总时间 `≥ 5%`。 | **不需要任何布局优化。** 仅遵守 §4.2 的 POD 纪律与可读性要求；禁止预防性对齐、禁止手写 padding、禁止提前 SoA 化。 |
| **Q2 跨界吗？** | 是否跨越 DLL 接口、插件 ABI、GPU 渲染管线、磁盘二进制格式或脚本语言边界？ | 不跨界 ⇒ 布局属私有实现细节，可自由演进；跨界 ⇒ 必须按 §4.3 施加逐字段 `offsetof` 断言与世代指纹，且“等大小改动”也必须同步两侧。 |
| **Q3 同频吗？** | 结构体内所有字段是否在同一个处理循环中以相同的频率被读写？ | 不同频 ⇒ 必须实施**冷热拆分**（将冷数据剥离为独立组件或二级结构）；拆分改动需提供访问模式证据或实测吞吐提升。 |
| **Q4 可证伪吗？** | 改动能否被一句话判定并在一条终端命令下被机器证伪（基准数字 / `static_assert` / ctest 门禁）？ | 不能证伪 ⇒ **一律拒绝合入**。必须补充编译期断言或基准测试用例，二选一。 |

### 一票否决（任一命中即拒绝合入）

1. **无基准证据的预防性优化**：缺乏实测数据背书的预防性对齐、手工 padding、预取指令或显式 SIMD 内建（Q1 = No 时尤甚）。
2. **跨界单重断言**：跨边界结构体仅有总尺寸 `sizeof` 断言，缺失关键字段逐个 `offsetof` 断言（无法防御等大小重排）。
3. **组件污染**：schema 注册组件中出现非平凡成员（如 `std::string`、`std::vector`、`Ref<T>`、虚函数表指针或裸指针资源句柄）——除 schema 显式豁免白名单外一律拒绝。
4. **无名填充垫片**：为对齐需要而插入无意义填充数组，且未附加注释解释对齐理由与实测收益。
5. **侵入式打包**：手写 `#pragma pack(n)` 强行压缩内存试图迎合后端；正解是显式成员降序排列或针对性 `alignas`。
6. **并发写跨线破坏**：将多个线程并发写入的热字段与其它只读或无关字段挤在同一 64B cache line（违反 R3 且无豁免登记）。
7. **热字段出线**：热访问字段因顺序不当被推到第一条 cache line（64B）之外，且无实测收益或豁免背书。
8. **反向重排**：仅仅为了“节省 4~8 字节空洞”而重排成员，却将核心热字段挤入第二条 cache line（违反 §4.8 的 R1 > R2 优先级）。

## 4.2 类型四分类 × 强制机制

针对不同场景的数据结构，严格套用对应的预算上限与强制门禁：

| 分类 | 典型示例 | 尺寸预算 | 平凡性要求 | 强制约束机制 |
| --- | --- | --- | --- | --- |
| **C1 组件 (schema 注册)** | `TransformComponent`、`MeshRendererComponent` | **`≤ 64B`**（单条 CPU cache line）；特例走豁免表 | 必须 `is_trivially_copyable` | 编译期模板实例化断言（`MakeComponentStorage<T>`）+ 自动化 ctest 反射枚举校验（门禁 A：`World.ComponentLayout`）。 |
| **C2 热路径临时 / 批量结构** | `InstanceData`、`LightUniforms`、排序键、`RenderExtract` 条目 | 视实测而定；优先控制在 `≤ 64B` 或显式固定 stride | 必须为 POD 结构体 | 逐字段 `offsetof` 编译期断言；若 `≥ 1000/帧` 或耗时 `≥ 5%`，必须将微基准数字固化于知识库。 |
| **C3 跨边界 ABI 结构** | `WeHostApi`、`WeComponentDesc`、`Scene` 宿主接口 | 不设尺寸上限，但必须具备版本锁与逐字段断言 | 依接口契约定义 | 结构体大小版本门（`StructSize`）+ 偏移哈希世代指纹（门禁 B/C：`World.RuntimeContract`）。 |
| **C4 磁盘 / 二进制格式** | `.wd` 字段、`.wtex` / `.wmodel` 头部、顶点 stride | 依格式规范版本锁死 | 不适用 | 遵循“只增不删”与版本升级协议；禁止直接 `memcpy` 结构体持久化，全量依赖 schema 字段名与 ID 反序列化。 |

## 4.3 跨边界布局的三条硬规则

1. **双重断言（Double Assertions）**  
   每一个跨越编译单元或硬件边界的结构体，必须同时具备**整尺寸断言**与**关键字段逐个 `offsetof` 断言**（门禁 C 已覆盖 `Renderer3D.h`、`Renderer3D_Internal.h`、`Mesh.cpp`、`WModelIO.h`）：
   ```cpp
   static_assert(sizeof(ObjectUniforms) == 144, "ObjectUniforms size mismatch");
   static_assert(offsetof(ObjectUniforms, EntityId) == 128, "ObjectUniforms.EntityId offset drift");
   ```
   *目的：防止在结构体总尺寸不变的情况下，成员顺序微调或类型置换引发静默的着色器错位或内存崩溃。*

2. **世代指纹（Generation Fingerprints）**  
   宿主主程序（`Editor.exe` / `Runtime.exe`）与核心动态库（`WorldRuntime.dll`）之间的布局一致性，必须通过成员偏移与尺寸的组合哈希（FNV-1a 指纹）在运行时握手校验，严禁仅依靠 `sizeof(Scene)`。  
   **实测证伪依据（2026-10-05 变异实验）**：  
   人为将 `Scene` 的两个同尺寸 `uint32_t` 成员换位，`sizeof(Scene)` 恒定保持为 `1640 字节`（纯尺寸检查完全失灵）；而指纹计算由 `9904454385323809073` 剧烈漂移为 `16225216100858202729`，门禁 B 立即触发红灯。  
   若指纹不匹配，系统输出明确差异并以安全退出码（Exit Code 3）退出，阻止进入未定义行为。

3. **两侧同改（Bilateral Synchronization）**  
   任何导致跨边界数据结构布局变更的提交，必须同时更新生产者与消费者两端代码，并在同一次构建流水线中通过门禁验证；只重建或提交一侧视同未经验证的严重违规。

## 4.4 数值预算（硬性指标）

- **ECS 组件**：单条 cache line 上限 **`64 字节`**（C1）。超出者必须在 `ComponentLayoutBudget.h` 登记白名单。
- **UBO / 实例缓冲**：C++ 结构体字段布局必须完全镜像着色器中的 `std140` / `std430` 声明；在 `std140` 下短向量（`vec3`）一律使用 `vec4` 对齐承载，严禁裸存 12 字节紧凑向量。
- **每帧堆分配**：主渲染与物理更新循环内**堆分配次数必须为 0**；单帧瞬态内存一律经由 `FrameArena`（帧线性分配器）申请。
- **热路径遍历**：每帧遍历实例 `≥ 1000` 的核心热循环内部，严禁包含虚函数调用、`std::function` 回调及基于哈希表的逐实体查询（必须转化为平坦数组遍历与基于世代索引的 O(1) 句柄解析）。
- **SIMD 指令假设**：在启用任何显式 SIMD / AVX2 矢量化之前，必须证明该路径符合 Q1 准则；由于组件池存储目前未对齐到 16/32 字节边界，严禁对组件连续内存做出对齐加载（aligned load）的前提假设。

## 4.5 反模式清单

出现下列模式即判定为架构违规，必须改写或提交正式豁免申请：

1. **组件内布尔脏标记**：在组件内放置 `bool IsDirty`。不仅破坏结构体对齐、占用珍贵 cache line，还会引入分支预测开销；正解为使用集中式版本号（Tick / Version Counter）或变更位图。
2. **动态资源进组件**：组件直接持有 `std::string`、`std::vector`、`Ref<T>` 或裸句柄；正解为使用平坦化句柄（`NameId` / `PathId` / `AssetId`）或定长嵌入式类型（`InlineString<N>`）。
3. **无断言的“外观优化”**：仅因视觉整洁而调整结构体字段声明顺序，但未同步补全 `static_assert`，导致后续维护发生静默回归。
4. **冷热数据同居**：将编辑期调试名称、统计计数器、配置选项与每帧物理/渲染计算所需的位置、变换混合在同一个结构体内。
5. **小对象过度隔离**：在总数小于 100 实例的冷路径对象上实施复杂的手工内存对齐或内存池管理。
6. **紧凑打包引发未对齐**：使用 `#pragma pack(1)` 压缩磁盘或传输结构，导致 CPU 在访问多字节整型/浮点时产生硬件未对齐访问异常或性能降级。

## 4.6 例外与登记（豁免白名单机制）

- 任何偏离 §4.2–§4.4 规范的结构体，必须显式登记在代码库的中央豁免表（`Engine/src/World/Scene/ComponentLayoutBudget.h`）；
- 豁免条目必须包含三项基本要素：**类型名称**、**架构论证理由**、**设定的到期复核日期**；
- **豁免是受控白名单，不是宽容度**：未在豁免表登记而超标的类型直接触发编译错误；超过复核期限的豁免条目在 ctest 门禁中产生警告，督促团队重审。

## 4.7 不需要本标准的场景（防御过度工程）

为了避免团队陷入无意义的微优化泥潭，以下场景**明确豁免**执行本标准：

1. **编辑器与离线工具**：WUI 面板代码、属性检查器、导入导出管线、开发期调试视窗；
2. **冷加载与初始化路径**：游戏启动配置解析、场景反序列化装载、关卡切换一次性初始化；
3. **低频对象**：整个游戏生命周期内全局实例总数 `≤ 100` 的逻辑实体；
4. **纯业务逻辑重构**：不涉及数据在内存中的存储排布、不改变 C1–C4 数据接口的逻辑流程重构；
5. **未经测量的性能直觉**：任何基于“我觉得这里对齐一下会更快”的猜想，严禁直接改动代码布局（可保留 `// PERF-HYPOTHESIS:` 注释并在任务台账中记录待测）。

## 4.8 成员顺序与填充（成员顺序是性能变量，不是风格问题）

**核心结论：成员顺序直接在底层硬件层面决定四项关键性能指标，因此属于架构标准强制管辖范围。**

### 四类物理影响面

| 影响面 | 物理硬件机制 | 实际性能后果 |
| --- | --- | --- |
| **M1 跨线拆分 (Cache Line Crossing)** | 热字段被前置冷字段推后，导致其内存地址横跨两条 64 字节 cache line 边界（`offset % 64 + size > 64`）。 | 每次访问该热字段必须触发两次 L1 数据缓存命中或两次独立的缓存行载入，使吞吐量减半。 |
| **M2 填充浪费 (Padding Bloat)** | 编译器遵循对齐规则自动在小尺寸字段后填充空洞（如 `bool, double, bool` 产生 24 字节，重排为 `double, bool, bool` 仅占 16 字节）。 | 增大连续数组的有效步长（stride），降低单条 cache line 内有效载荷密度，浪费内存带宽与容量。 |
| **M3 伪共享 (False Sharing)** | 多个并发线程各自高频写入**不同字段**，但这些字段碰巧分配在同一条 64 字节 cache line 内。 | 硬件缓存一致性协议（MESI）导致该 cache line 在不同 CPU 核心之间反复失效颠簸（ping-pong），多核吞吐严重暴跌。 |
| **M4 访问簇分离 (Access Cluster Dispersion)** | 在同一计算循环中总是被同时读取的字段被分散在不同 cache line，或高频写入字段与静态只读字段紧挨在一起。 | 打散访存局部性，增加所需缓存行总数；高频写入字段导致只读字段所在缓存行被反复置为脏行并强制同步。 |

### 可执行的成员顺序规则（R1–R6）

- **R1 热字段前置且不跨线（Hot Fields First & Contained）**  
  结构体的高频读写字段必须置于声明最前端，且必须保证：  
  $$\text{offsetof}(T, \text{HotField}) + \text{sizeof}(T::\text{HotField}) \le 64$$  
  确保所有核心热数据完全容纳在第一条 cache line 内。冷数据（元数据、统计、调试开关）统一放置在尾部或剥离至扩展结构。  
  *证据义务*：编写编译期断言锁定热字段偏移范围。

- **R2 零空洞优先（Zero Padding via Alignment Descending）**  
  POD 结构体内部成员默认按照字段的 `alignof` **严格降序排列**（8 字节对齐成员 → 4 字节 → 2 字节 → 1 字节），使 $\text{sizeof}(T)$ 精确等于各个成员大小之和。任何刻意保留的空洞必须附带架构解释。  
  *证据义务*：自动化门禁校验结构体大小与各成员大小累加值之差。  
  **冲突裁决（R1 vs R2）**：当降序排列（R2）会导致核心热字段被挤出第一条 cache line（违反 R1）时，**R1 具有绝对优先权**——访存局部性与缓存命中率优先于微小的空间紧凑性。

- **R3 伪共享物理隔离（False Sharing Physical Isolation）**  
  任何在多线程环境中可能被不同工作线程并发高频写入的变量，必须强制进行缓存行对齐隔离：  
  `alignas(64)` 且附加 `static_assert(sizeof(T) % 64 == 0)`；对于线程池局部计数器，必须采用 per-worker 槽位隔离设计。  
  **仓库实证案例**：`Engine/src/World/Core/Thread/JobSystem.cpp:20-37` 中，六个高频统计原子（`s_StatExecuted`、`s_StatStolen`、`s_StatExecutedWhileWaiting`、`s_StatOverflowPushes`、`s_StatQueueHighWater`、`s_StatWaits`）与每次 Kick/Complete 都会写入的 `s_PendingJobs` 混住在同一条 64 字节 cache line 内，导致所有工作线程发生全核乒乓颠簸（已列入 F7 修订）。  
  *证据义务*：并发写入变量必须登记在专属并发清单中，并包含行隔离编译期断言。

- **R4 访问簇紧密聚合（Access Cluster Packing）**  
  在同一热循环内被同时访问的字段，声明时必须物理相邻，以最大化空间局部性，使其尽可能容纳在最少数量的缓存行中。重排顺序必须引用调用点的访问模式作为依据。

- **R5 首成员即热入口（Hot Entrypoint at Offset Zero）**  
  结构体最常被解引用的核心入口字段应放置在偏移 0 处（`offsetof(T, Primary) == 0`）。使结构体首地址直接等价于热数据地址，节省基址加偏移的运算开销，并为指针别名与直接类型转换提供安全保障。

- **R6 顺序改动双向登记（Paired Registration of Reordering）**  
  结构体成员顺序的微调被正式定义为**结构布局破坏性改动**。改动后必须同步更新布局快照测试（门禁 A）与跨模块接口指纹（门禁 B）。严禁认为“总尺寸没变就可以随意调换顺序”。

### 一票否决补充条款

6. 将多线程高频并发写入的原子变量与其它普通状态字段混存在同一 64B 空间（严重违反 R3）。
7. 热数据访问成员偏移越过 64 字节分界线且无法提供基准收益证明（违反 R1）。
8. 为了消除局部几个字节的填充空洞而打乱成员，导致主计算字段溢出至第二条缓存行（违反 R1 > R2 优先级准则）。

### 反模式补充条款

- **细碎字段夹心**：在两个 8 字节对齐的热字段之间插入单字节 `bool` 或微小枚举，人为撕裂内存并制造空洞。
- **混合脏化缓存**：将多线程运行期的统计计数器（如 `TasksCompleted`）紧挨在只读配置结构体旁边，导致读取配置的核心不断受到写入核的缓存行作废惩罚。
- **平铺原子变量数组**：将每个 worker 线程的高频任务计数声明为连续数组 `std::atomic<uint64_t> counter[N];`（全部落入同一条缓存行疯狂冲突）。
- **无感重排**：在重构代码时仅因 IDE 格式化或个人美感随意重排字段，未验证对齐门禁。

## 5. 需要修复清单（正确性 / 防护缺口）

当前引擎中已识别的布局防护缺口与修复方案定义如下：

| 编号 | 问题描述 | 现状事实与证据 | 修复方案与工程手段 | 优先级 |

### 6.1 裁决结果(2026-10-05;数字即下表,口径与跑法见 §6.3)

优化项的**唯一**准入方式是数字。下表是已跑过基准的课题与结论 —— 包括"不做"的结论,
因为"不做"同样是结论,而且必须写下来(否则下一轮又会有人凭直觉去改)。

| 课题 | 裁决 | 实测依据(Release,本机) |
| --- | --- | --- |
| **物理插值状态存 TRS 而非局部矩阵**(68B → 44B) | ✅ **已落地** | 遍历 68B 状态 **1.435** ns/元素 vs 44B 状态 **0.589** ns/元素(中位)。同时省掉写侧每固定步一次 `Compose`、读侧每帧两次矩阵分解 —— 因为原实现本来就是"合成了又拆开"(`InterpolateRigidTransform` 要 normalize 三列再 `quat_cast`)。布局棘轮:`Components.h` 的 `static_assert(sizeof == 44)` |
| **`/arch:AVX2`** | ❌ **不做** | 同源 A/B(同一份 `.cpp`,只有 `/arch` 不同):SSE2 中位 **10.81** ns/元素 vs AVX2 中位 **10.49** ns/元素,差异 ≈3% 且落在两组分布重叠区(SSE2 10.18–11.12,AVX2 10.01–11.42)⇒ **无实测收益**。代价不止"没用":它抬高全仓最低 CPU 要求,并改变浮点码型(与 P4/P5/P6/P7 的逐位可复现承诺存在风险) |
| **`GLM_FORCE_ALIGNED_GENTYPES`** | ❌ **不做** | packed(当前,`alignof=4`)中位 **3.442** ns/元素 vs align16 中位 **3.606** ns/元素;7 轮里 6 轮 packed 不差 ⇒ 对齐加载**没有**换到收益。而打开它会把 `alignof(glm::mat4)` 抬到 16,平移**所有**含矩阵的组件布局 ⇒ 连带撞门禁 A(尺寸预算)与门禁 B(偏移指纹) |
| **`WorldTransformComponent` 对根实体的"冗余"** | ❌ **不做** | 根实体的世界矩阵确实等于局部矩阵,但它是渲染/物理的**读取热路径**。改成按需派生要付出 `Compose`(实测 **10.7** ns/实体/帧,见 F 项),而读一份已在缓存里的 64B 只有 ~1 ns 量级 ⇒ 收益为负(判定四问 Q1 = No:不是"热就优化",而是"优化要真的更快") |
| **线程池热原子去伪共享** | ✅ **结构已落地,收益不可分辨** | 见 §6.2。保留理由不是"量到了加速",而是 R3 是硬规则 + 代价仅 448B 静态内存 + 有编译期断言兜住 |
| **帧内高频结构跨线体检(O5)/ 组件成员热力分布(O7)** | ⬜ **未测 ⇒ 不做** | 尚未跑基准。按 §4.1 Q1,没有数字就不动布局 |

### 6.2 F8「自动空洞审计」的裁决:先量化,再决定建不建工具

原计划让门禁 A 自动推导"成员尺寸和"并与 `sizeof` 比较,从而发现**内部空洞**(§4.8 R2)。
本轮用一次性探针把 22 个 schema 组件全部审计了一遍(**实测偏移,不是推算**),结论如下 ——
**自动工具暂不构建**,理由是"问题比想象的小";而"不做"同样是必须写下来的结论。

| 组件 | sizeof | 成员尺寸和 | 内部空洞 | 去掉后 stride 变吗 |
| --- | --- | --- | --- | --- |
| `MeshRendererComponent` | 64 → **56** | 56 | 4B(偏移 20–23) | ✅ 64 → 56 |
| `SkinnedMeshRendererComponent` | 64 → **56** | 50 | 4B(20–23) + 3B(45–47) | ✅ 64 → 56 |
| `RigidBody2DComponent` | 16 | 14 | 2B(偏移 6–7) | ❌ 不变(被尾部填充吸收) |
| `RigidBody3DComponent` | 40 | 35 | 2B(偏移 26–27) | ❌ 不变(被尾部填充吸收) |
| 其余 18 个 | — | — | 无 | — |

**关键判据不是"有没有空洞",而是"去掉空洞会不会真的缩小 stride"** ——
空洞若已被尾部对齐填充吸收,去掉它 `sizeof` 一字不变,那就是纯美观问题,不值得动布局。
按这个判据只有 2 个组件值得改,已按 R2 重排(8B 对齐的 `AssetRef` 先排、4B 标量其次、
1B `bool` 最后)落到 **56B**,并在 `Components.cpp` 用 `static_assert(sizeof == 56)` 钉住
(插回一个 4B/1B 字段就会回到 60/64 ⇒ 编译失败)。

**为什么不做自动工具**:为 2 个组件建一套"生成器输出字段偏移 + 门禁比对"的机制,收益/成本
不划算;而且它有**假阳性**风险 —— 组件里凡有非 schema 成员(如 `TransformComponent` 的
`Flags`/`_Padding`)或 `Transient` 字段,按"相邻 schema 字段"推导出的"空洞"根本不是空洞。
真要做,应作为独立任务设计(生成器输出布局表 + 显式豁免),而不是塞进门禁 A。

**留作未来的触发器**:若某个**热**组件被发现跨线/空洞明显(有帧时间证据),再按上表口径
单独审计它 —— 判据仍是"stride 会不会变",不是"看起来齐不齐"。

**踩坑记录(改布局时必读)**:改组件布局后**必须整仓 `ALL_BUILD` 再跑测试**。
只构建单个测试目标时,测试 EXE 与 `WorldRuntime.dll` 可能世代不一致 ——
EXE 按新偏移写组件、DLL 按旧偏移读,表现为"某个字段读成 0"这类假故障
(本次实测:`SkinnedMeshRendererComponent` 重排后 `Time` 恒为 0,追查到最后是
**EXE/DLL 布局不一致**,不是重排本身的问题;`ALL_BUILD` 后同一改动全绿)。
这正是门禁 B(宿主 ↔ DLL 偏移指纹)存在的理由 —— 它是那条一致性契约的运行时守卫。

### 6.3 基准怎么跑(可复跑)

`WorldLayoutBenchmarks` 是**手动目标,不进 ctest** —— 基准依赖机器与负载,不适合当每次提交
都必绿的门禁。它有两个目标:默认(SSE2)与 `WorldLayoutBenchmarksAvx2`(同一份源码 + `/arch:AVX2`,
用于 O3 的同源 A/B)。

```powershell
cmake --build build/x64-Debug --config Debug --target WorldLayoutBenchmarks WorldLayoutBenchmarksAvx2
build/x64-Debug/tests/Debug/WorldLayoutBenchmarks.exe        # 用例 A–G
build/x64-Debug/tests/Debug/WorldLayoutBenchmarksAvx2.exe    # 只用于对比 F 项(O3)
```

**关键前提**:回答 O3/O4 这类**计算**问题必须用 Release —— Debug(`/Od`)下编译器不做向量化,
`/arch:AVX2` 结构上无从发挥,测出来的"没差别"是无意义的。O1 那类**访存**问题在 Debug 下方向
已可辨,但数字仍以 Release 为准。同理,基准自身也必须守 R3:探针里被多线程并发写的计数器
要 `alignas(64)` + `atomic`,否则量到的是探针自己的伪共享。

## 6.5 SIMD 使用规则

> 与 §4 同一决策面,不另开标准。**SIMD 不是性能问题的默认答案** —— 本节的主要作用之一是
> **拦住**无收益的 SIMD 化。

### 6.5.0 判定双轴(先看这条:单看"热"会得出错误结论)

SIMD 只有两种**正当**理由,必须至少命中一条:**A 吞吐轴**(ALU 受限)或 **B 操作数/分支轴**。

| 轴 | 判据 | 典型形态 |
| --- | --- | --- |
| **A 吞吐轴** | 算术强度 = 浮点运算数 ÷ 读入字节数。**≥ 10 flops/byte** 才可能 ALU 受限;**< 3** 判"内存受限 ⇒ 拒绝 SIMD"(SIMD 只把 ALU 时间推向 0,总时间由内存流量决定) | 大规模粒子、软体、稠密线性代数 |
| **B 操作数/分支轴** | 单元素循环里含**可 4 路并行、且每元素都有早退分支**的判定。SIMD 跨对象批处理(4 对象/批)可把指令数降到约 1/4 **且完全无分支** | 视锥剔除、批量区间/包围盒判定、逐元素筛选 |

**为什么必须有 B 轴**(实测修正):视锥剔除每 AABB 约 60 个标量操作 ÷ 24B ≈ **2.5 flops/byte**,
按 A 轴会被拒;但它的真实代价是**每个平面一次早退分支**(6 次/对象),而这些分支在"大多可见"
的场景里几乎从不早退 ⇒ 纯属预测压力。把 4 个对象放进 4 个 lane、按平面循环,每批只做约 60 个
**向量**操作(≈15/对象)且无分支 ⇒ 指令数约 1/4。**只用 A 轴会漏掉这一类真实收益。**

**怎么快速算 A 轴**:数循环体里的 `+ - * /`、`dot`、`normalize`、矩阵乘法等浮点运算次数,
除以每元素读到的字节数。矩阵乘法按实际乘加次数数(`mat4*mat4` = 64 乘 + 48 加)。

### 6.5.1 实现优先级(P0 → P2,先试前面的)

1. **P0 让编译器和库做**:表达成循环让自动向量化生效(SoA、去分支、定长、无别名)。
   `glm` 的 `vec4`/`mat4` 在 x64 上**本身已是 SSE2**(glm 1.0.3 自动检测)—— 先用库表达意图。
   **手写 intrinsics 必须能说清"库/编译器为什么做不到"**。
2. **P1 改数据布局**:把内存受限换成 ALU 受限(合并结构、减少字段、SoA 拆分)。
   本仓库实测这一层收益比 SIMD **高一个数量级**(步长 ±44% vs AVX2 ≈3%)。
3. **P2 手写 intrinsics**:P0/P1 都试过且至少命中一条轴,才允许。

### 6.5.2 硬规则

- **S1 集中化**:手写 intrinsics 只允许出现在 `Engine/src/World/Math/Simd/`(允许清单)。
  其它位置出现 `_mm_`/`_mm256_`/`_mm512_`/`__m128`/`__m256`/`vld1q_` 等 ⇒ **门禁 E 红灯**。
- **S2 显式依赖**:每个 intrinsics 文件显式包含对应架构头,**不得依赖传递包含**。
- **S3 回退**:每个 SIMD 路径必须有等价标量回退,且**两条路都被测试**;用 `#if` 按架构选择,
  不得出现无保护的目标专用代码。
- **S4 确定性**:改变浮点结果的 SIMD 默认关闭并门控。**逐 lane 与标量同序**的写法可以默认开启
  (因为逐位一致);一旦改变运算顺序/引入 FMA 收缩/开 FTZ,就必须门控 ——
  引擎对 P4/P5/P6/P7 有"逐位可复现"的已交付承诺。
- **S5 禁止顺手全局开 SIMD**:`/arch:*`、`GLM_FORCE_ALIGNED_GENTYPES` 是**全仓决定**,会平移
  所有组件布局并连带撞门禁 A/B(已有先例),必须单独方案 + 全量回归。
- **S6 先排除更便宜的**:算法复杂度 → 内存流量/步长/伪共享 → 每帧堆分配 → 分支与虚调用。
  四条都排除后才轮到 SIMD。

### 6.5.3 基准协议

- 用既有同源双目标:`WorldLayoutBenchmarks`(SSE2)与 `WorldLayoutBenchmarksAvx2`(同 .cpp + `/arch:AVX2`,
  A/B 只差一个变量)。**必须用 Release**:Debug(`/Od`)下编译器不向量化,"测出没差别"无意义。
- 报**中位数 + 分布**,同报算术强度(解释为什么有/没有收益)。**总时间差 < 5% 判"无收益"**,保留更简单的实现。
- "不做"同样是结论,必须写下来(否则下一轮又会有人凭直觉去改)。

### 6.5.4 反模式

- 逐分量 `_mm_set1_ps` 广播去"向量化"**单个** vec4 运算 —— 既不是 SoA 也不是批量,与编译器/glm
  生成的代码等价,只是更脆。
- `_mm_storeu_ps` 到临时数组再逐元素拷进目标(store-to-load forwarding 惩罚)。
- 靠传递包含拿到 `__m128`(换编译器/PCH 顺序即断)。
- 无 guard 的目标专用代码。
- 为 SIMD 把 AoS 组件数组当对齐数据加载(组件不保证 16/32B 对齐)。
- 把"注释里写了 SIMD"当成已有基建。

### 6.5.5 不需要本规则的场景

- 一次性初始化、读档、构建期脚本、编辑器/工具面板;实例数 ≤ 100 或非每帧路径;
- 已被 A 轴判定为内存受限的循环(要做的是布局/流量优化);
- 纯标量语义的公共 API 表面(不要把向量类型泄漏进组件或 schema)。

### 6.5.6 何时重评"引入 SIMD 库"

当前**不引入**(没有通过双轴的循环,引入 xsimd/highway 只会扩大维护面并诱导表达式级 SIMD,
见 ADR 0009)。出现下列任一条才重评:① 出现通过 A 轴的 ALU 受限热点(有帧时间占比证据);
② 新增 ARM64/NEON 目标(此时 S1–S3 的封装与回退从纪律变成必需);
③ 引入算术强度天然很高的新负载(大规模粒子/软体/集群 AI);
④ glm 表达不了、编译器又自动向量化不了的批量数学成为瓶颈。

### 6.5.7 现有实现盘点(2026-10-05 实测)

| 位置 | 现状 | 处置 |
| --- | --- | --- |
| glm 自带 SSE2 后端 | **隐式生效**(x64 默认),`vec4/mat4` 运算本已向量化 | 保留;本规则不再要求"自己写一遍" |
| `Math::MultiplyMat4ByVec4_SIMD_x4` | 全仓唯一手写 intrinsics;**未测量**、缺显式头文件、无 guard/回退、与 glm 路径重复 | 实测对照后**删除并统一走 glm**(见 §6.6) |
| `AabbInFrustum`(视锥剔除) | 命中 **B 轴**:6 次/对象的早退分支 | **改为跨对象批处理 SIMD**(4 对象/lane,逐 lane 与标量同序 ⇒ 逐位一致),见 §6.6 |
| 其余热点(阴影包围盒归约、变换组合、骨骼调色板) | 算术强度 ≈0.5–1.4 flops/byte ⇒ 内存受限 | 按 A 轴**不做**;要做先补帧时间证据 |

### 6.6 SIMD 落地与实测(2026-10-05)

**新增**(S1 的允许位置):`Engine/src/World/Math/Simd/`

| 文件 | 内容 |
| --- | --- |
| `SimdConfig.h` | 架构门(`WLD_SIMD_SSE2`)+ 显式包含架构头(S2)。刻意不假设"我们永远是 x86-64" |
| `FrustumCullSimd.h` | AABB×视锥的**批量**判定(4 对象/lane)+ 标量回退 + 标量参考实现(同文件邻近,防口径漂移) |
| `Mat4xVec4Batch.h/.cpp` | mat4 × 4×vec4 批量变换(唯一保留的手写 intrinsics)+ 标量回退 |

**门禁 E**:`tools/agents/check-simd.ps1` + ctest `World.SimdPolicy` —— 允许目录之外出现
`_mm_`/`__m128` 等记号即红灯。**只判代码不判文本**(先剥离注释;否则"在注释里讨论 `_mm_set1_ps`"
会误报,而误报会让人开始无视门禁)。判别力已实测:注入一处违规 ⇒ 红灯;移除 ⇒ 绿灯。

**对照测试**:`Tests/World/SimdTests.cpp` + ctest `World.Simd` —— 证明①批量 SIMD 与逐对象标量
**逐字节一致**(4096 随机 + 恰好落在平面上的边界样本 + count 0/1/2/3/4/5/7/8/63 的尾巴扫描);
②与渲染器权威实现 `AabbInFrustum` 同口径;③**有判别力**(把一个平面推远,可见集合必须真的改变,
否则"一致"可能只是"两边都全可见"式假通过)。

#### 裁定一:视锥剔除改批量 SIMD —— **采纳**(命中 B 轴)

Release,4 次复现,ns/draw(16384 draw,5935 可见):

| 实现 | ns/draw |
| --- | --- |
| 逐对象标量(`AabbInFrustum`) | 10.56 / 10.62 / 12.65 / 14.26 |
| 批量(batch,不含取样) | 4.99 / 4.54 / 4.87 / 4.70 |
| **分块(tiled,= 渲染器实际路径)** | **5.39 / 5.25 / 5.26 / 5.46** |

主打数字用 **tiled**(那才是上线跑的东西):**≈2.0–2.2×**,而 tiling 的 AoS→SoA 取样只多花
约 10%(batch 4.7–5.0 vs tiled 5.3)。**可见计数两边都是 5935,逐帧一致** ——
这是集成级的旁证:分块路径与逐对象标量给出同一可见集合。

这是 **B 轴**的实证:该循环算术强度只有 ≈2.5 flops/byte(A 轴会判"内存受限、拒绝 SIMD"),
但它的真实代价是**每对象 6 次早退分支**;跨对象批处理把它们全部消掉。
**结论:只用 A 轴会漏掉这一类真实收益 —— 这是本节必须有第二条轴的原因。**

**并行粒度必须与改造前对齐**:旧代码 `batchSize = 64 draw/job`;若按"1 tile(16 draw)/job"
调度,单 job 工作量只剩 ≈70ns,调度开销会吃掉收益 ⇒ 用 `batchSize = 4 tile = 64 draw/job`。

**端到端复核**(1024 网格压力场景,`verify-perf3d.py`):把渲染器临时换回**标量**剔除再跑同一
探针,两者给出**完全相同**的 `visible=338 / culled=686`,且画面非背景占比同为 `53.268%`;
更关键的是探针自带的最强断言——**剔除开/关两帧逐像素一致**(`diffPixels=0`)——也通过。
即:改 SIMD 前后**可见集合与像素输出都不变**(剔除是纯优化),性能是净收益。


#### 裁定二:2D quad 顶点变换的手写 intrinsics —— **保留并合规化**(不是删)

Release,3 次复现,ns/quad(4096 quad):

| 写法 | ns/quad |
| --- | --- |
| 手写 SSE(现有实现) | 3.79 / 3.53 / 3.56 |
| glm 朴素循环(`out[c] = m * corners[c]`) | 5.86 / 5.92 / 5.83 |
| glm 提升列写法(显式取 `m[0..3]` 再用 vec4 运算) | 7.56 / 7.48 / 7.62 |

**手写版比"最好的可移植写法"快约 2.1×** ⇒ 按 §6.5.1 的 P0("先用库表达")**已被排除**,
保留 intrinsics 并登记。真正的原因是它把**矩阵的 4 个列提升到顶点循环之外**再复用 4 次 ——
这条结构性收益用 glm 没能复现出同等代码质量。

**注意这条推翻了一个直觉**:一开始预期"glm 在 x64 本就 SSE2,手写版应无优势";实测相反。
这正是 §4.1 Q4"可证伪"和 §6.5.3"必须测量"的价值 —— 没有数字就会删错东西。
处置:移入 `Math/Simd/`(`Mat4xVec4Batch4`),补显式架构头与标量回退,
原 `Math::MultiplyMat4ByVec4_SIMD_x4` 保留为同名薄转发(调用方与结果都不变)。

#### 未做(按双轴 + 帧时间证据)

- 三维热点的其余候选(阴影包围盒归约、`TransformAabb`、骨骼调色板):算术强度 ≈0.5–1.4 flops/byte,
  且**没有帧时间占比证据** ⇒ 按 §6.5.0 不做。要做先补证据。
- `ComputeCirclePositions` / `DrawRectCore` 与 quad 路径的三份实现**未合并**:它们走 glm 路径,
  合并到 SIMD 会改变浮点结合顺序(逐位结果可能变化),需要像素基线复跑才能确认 ——
  收益(2D 圆形/线框的顶点变换)未证明占帧时间 ⇒ 暂不动,登记为已知重复。


## 7. 门禁能力边界（抓得住 vs 抓不住）

本体系设计三组互相配合的自动化门禁，其防御边界界定如下（严禁夸大单组门禁的能力）：

| 门禁标识 | 覆盖范围与测试目标 | **抓得住（100% 拦截）** | **抓不住（需要其他手段兜底）** |
| --- | --- | --- | --- |
| **门禁 A**<br>`World.ComponentLayout` | 所有注册进 Schema 的组件 + 豁免表核对 | 1. 组件 `sizeof > 64B` 且未在豁免表登记；<br>2. 引入非平凡可拷贝成员（编译期 `MakeComponentStorage<T>` 直接报错）；<br>3. 组件尺寸发生变更而未同步基线快照。 | 1. 组件内部同尺寸字段重排（`sizeof` 不变且无字段级 offsetof 覆盖）；<br>2. 内部空洞浪费（未超过空洞上限）；<br>3. 未注册进 schema 的隐式逻辑组件（需由宏/手写断言兜底）。 |
| **门禁 B**<br>`World.RuntimeContract` | `Scene`、`WorldContext` 宿主 ↔ DLL 跨模块契约 | 1. 结构体总尺寸变化；<br>2. **关键成员等大小重排、位移、类型替换**（实测 `sizeof=1640` 不变，指纹从 `9904454385323809073` 突变为 `16225216100858202729`，直接红灯拦截）；<br>3. 跨模块 ABI 协议版本不一致。 | 1. 指纹采样清单之外的尾部私有指针成员顺序微调；<br>2. 虚函数表内部槽位顺序变动；<br>3. 单一模块内部私有数据结构重排。 |
| **门禁 C**<br>（编译期） | GPU 侧结构体（UBO / 实例缓冲 / 骨骼）、磁盘头与顶点 stride | 1. `ObjectUniforms`、`InstanceData`、`BoneUniforms`、`LightUniforms` 逐字段偏移漂移；<br>2. 顶点属性 stride / 偏移变动；<br>3. 资产头（`WModelIO` / `Mesh`）二进制布局错位。 | 1. 动态生成或着色器端自定义的 SSBO 布局；<br>2. CPU 端未在 C++ 显式建模声明的临时常量；<br>3. 不跨边界的内部局部渲染临时变量。 |
