# 数据布局与性能标准 (v1)

> 面向**改引擎的人**与**后续接入开发的 AI**。
> 本文是可执行的工程规范与门禁判据，不是理论散文。
> 所有规则附带明确的**证据义务**（要写什么编译期断言、跑什么测试门禁、提供什么基准数字）。

---

## 4.0 谁读、什么时候读

任何改动满足下列任一条**之前**，先读完本文并执行 §4.1 的判定四问：

- 新增或修改**组件**（`Component`）、`schema` 字段、`entt` 池内数据结构；
- 新增或修改**跨边界结构体**：宿主 ↔ `WorldRuntime.dll`、插件 ABI、GPU 侧 UBO / 顶点 / 实例缓冲、二进制资产头、Lua usertype；
- 新增或修改**每帧遍历**的容器或**热路径**数据结构；
- 试图编写 `alignas` / `#pragma pack` / 手写填充字节（padding）/ 结构体数组（AoS）转数组结构体（SoA）拆分 / AVX / SIMD 内建函数。

---

## 4.1 判定四问（先判“需不需要”，再判“怎么做”）

在动手改动内存布局或引入优化之前，必须按顺序回答以下四个问题：

| 问 | 判据 | 答 "No" 的后果 |
| --- | --- | --- |
| **Q1 热吗？** | 该数据每帧被遍历的实例数 `≥ 1000`，**或**已有实测剖析（profiling）证据表明其占单帧总时间 `≥ 5%`。 | **不需要任何布局优化。** 仅遵守 §4.2 的 POD 纪律与可读性要求；禁止预防性对齐、禁止手写 padding、禁止提前 SoA 化。 |
| **Q2 跨界吗？** | 是否跨越 DLL 接口、插件 ABI、GPU 渲染管线、磁盘二进制格式或脚本语言边界？ | 不跨界 ⇒ 布局属私有实现细节，可自由演进；跨界 ⇒ 必须按 §4.3 施加逐字段 `offsetof` 断言与世代指纹，且“等大小改动”也必须同步两侧。 |
| **Q3 同频吗？** | 结构体内所有字段是否在同一个处理循环中以相同的频率被读写？ | 不同频 ⇒ 必须实施**冷热拆分**（将冷数据剥离为独立组件或二级结构）；拆分改动需提供访问模式证据或实测吞吐提升。 |
| **Q4 可证伪吗？** | 改动能否被一句话判定并在一条终端命令下被机器证伪（基准数字 / `static_assert` / ctest 门禁）？ | 不能证伪 ⇒ **一律拒绝合入**。必须补充编译期断言或基准测试用例，二选一。 |

### 一票否决（任一命中即拒绝合入）

1. **无基准证据的预防性优化**：缺乏实测数据背书的预防性对齐、手工 padding、预取指令或显式 SIMD 内建（Q1 = No 时尤甚）。
2. **跨界单重断言**：跨边界结构体仅有总尺寸 `sizeof` 断言，缺失关键字段逐个 `offsetof` 断言（无法防御等大小重排）。
3. **组件污染**：schema 注册组件中出现非平凡成员（如 `std::string`、`std::vector`、`Ref<T>`、虚函数表指针或裸指针资源句柄）——除 schema 显式豁免白名单外一律拒绝。
4. **无名填充垫片**：为对齐需要而插入无意义填充数组，且未附加注释解释对齐理由与实测收益。
5. **侵入式打包**：手写 `#pragma pack(n)` 强行压缩内存试图迎合后端；正解是显式成员降序排列或针对性 `alignas`。
6. **并发写跨线破坏**：将多个线程并发写入的热字段与其它只读或无关字段挤在同一 64B cache line（违反 R3 且无豁免登记）。
7. **热字段出线**：热访问字段因顺序不当被推到第一条 cache line（64B）之外，且无实测收益或豁免背书。
8. **反向重排**：仅仅为了“节省 4~8 字节空洞”而重排成员，却将核心热字段挤入第二条 cache line（违反 §4.8 的 R1 > R2 优先级）。

## 4.2 类型四分类 × 强制机制

针对不同场景的数据结构，严格套用对应的预算上限与强制门禁：

| 分类 | 典型示例 | 尺寸预算 | 平凡性要求 | 强制约束机制 |
| --- | --- | --- | --- | --- |
| **C1 组件 (schema 注册)** | `TransformComponent`、`MeshRendererComponent` | **`≤ 64B`**（单条 CPU cache line）；特例走豁免表 | 必须 `is_trivially_copyable` | 编译期模板实例化断言（`MakeComponentStorage<T>`）+ 自动化 ctest 反射枚举校验（门禁 A：`World.ComponentLayout`）。 |
| **C2 热路径临时 / 批量结构** | `InstanceData`、`LightUniforms`、排序键、`RenderExtract` 条目 | 视实测而定；优先控制在 `≤ 64B` 或显式固定 stride | 必须为 POD 结构体 | 逐字段 `offsetof` 编译期断言；若 `≥ 1000/帧` 或耗时 `≥ 5%`，必须将微基准数字固化于知识库。 |
| **C3 跨边界 ABI 结构** | `WeHostApi`、`WeComponentDesc`、`Scene` 宿主接口 | 不设尺寸上限，但必须具备版本锁与逐字段断言 | 依接口契约定义 | 结构体大小版本门（`StructSize`）+ 偏移哈希世代指纹（门禁 B/C：`World.RuntimeContract`）。 |
| **C4 磁盘 / 二进制格式** | `.wd` 字段、`.wtex` / `.wmodel` 头部、顶点 stride | 依格式规范版本锁死 | 不适用 | 遵循“只增不删”与版本升级协议；禁止直接 `memcpy` 结构体持久化，全量依赖 schema 字段名与 ID 反序列化。 |

## 4.3 跨边界布局的三条硬规则

1. **双重断言（Double Assertions）**  
   每一个跨越编译单元或硬件边界的结构体，必须同时具备**整尺寸断言**与**关键字段逐个 `offsetof` 断言**（门禁 C 已覆盖 `Renderer3D.h`、`Renderer3D_Internal.h`、`Mesh.cpp`、`WModelIO.h`）：
   ```cpp
   static_assert(sizeof(ObjectUniforms) == 144, "ObjectUniforms size mismatch");
   static_assert(offsetof(ObjectUniforms, EntityId) == 128, "ObjectUniforms.EntityId offset drift");
   ```
   *目的：防止在结构体总尺寸不变的情况下，成员顺序微调或类型置换引发静默的着色器错位或内存崩溃。*

2. **世代指纹（Generation Fingerprints）**  
   宿主主程序（`Editor.exe` / `Runtime.exe`）与核心动态库（`WorldRuntime.dll`）之间的布局一致性，必须通过成员偏移与尺寸的组合哈希（FNV-1a 指纹）在运行时握手校验，严禁仅依靠 `sizeof(Scene)`。  
   **实测证伪依据（2026-10-05 变异实验）**：  
   人为将 `Scene` 的两个同尺寸 `uint32_t` 成员换位，`sizeof(Scene)` 恒定保持为 `1640 字节`（纯尺寸检查完全失灵）；而指纹计算由 `9904454385323809073` 剧烈漂移为 `16225216100858202729`，门禁 B 立即触发红灯。  
   若指纹不匹配，系统输出明确差异并以安全退出码（Exit Code 3）退出，阻止进入未定义行为。

3. **两侧同改（Bilateral Synchronization）**  
   任何导致跨边界数据结构布局变更的提交，必须同时更新生产者与消费者两端代码，并在同一次构建流水线中通过门禁验证；只重建或提交一侧视同未经验证的严重违规。

## 4.4 数值预算（硬性指标）

- **ECS 组件**：单条 cache line 上限 **`64 字节`**（C1）。超出者必须在 `ComponentLayoutBudget.h` 登记白名单。
- **UBO / 实例缓冲**：C++ 结构体字段布局必须完全镜像着色器中的 `std140` / `std430` 声明；在 `std140` 下短向量（`vec3`）一律使用 `vec4` 对齐承载，严禁裸存 12 字节紧凑向量。
- **每帧堆分配**：主渲染与物理更新循环内**堆分配次数必须为 0**；单帧瞬态内存一律经由 `FrameArena`（帧线性分配器）申请。
- **热路径遍历**：每帧遍历实例 `≥ 1000` 的核心热循环内部，严禁包含虚函数调用、`std::function` 回调及基于哈希表的逐实体查询（必须转化为平坦数组遍历与基于世代索引的 O(1) 句柄解析）。
- **SIMD 指令假设**：在启用任何显式 SIMD / AVX2 矢量化之前，必须证明该路径符合 Q1 准则；由于组件池存储目前未对齐到 16/32 字节边界，严禁对组件连续内存做出对齐加载（aligned load）的前提假设。

## 4.5 反模式清单

出现下列模式即判定为架构违规，必须改写或提交正式豁免申请：

1. **组件内布尔脏标记**：在组件内放置 `bool IsDirty`。不仅破坏结构体对齐、占用珍贵 cache line，还会引入分支预测开销；正解为使用集中式版本号（Tick / Version Counter）或变更位图。
2. **动态资源进组件**：组件直接持有 `std::string`、`std::vector`、`Ref<T>` 或裸句柄；正解为使用平坦化句柄（`NameId` / `PathId` / `AssetId`）或定长嵌入式类型（`InlineString<N>`）。
3. **无断言的“外观优化”**：仅因视觉整洁而调整结构体字段声明顺序，但未同步补全 `static_assert`，导致后续维护发生静默回归。
4. **冷热数据同居**：将编辑期调试名称、统计计数器、配置选项与每帧物理/渲染计算所需的位置、变换混合在同一个结构体内。
5. **小对象过度隔离**：在总数小于 100 实例的冷路径对象上实施复杂的手工内存对齐或内存池管理。
6. **紧凑打包引发未对齐**：使用 `#pragma pack(1)` 压缩磁盘或传输结构，导致 CPU 在访问多字节整型/浮点时产生硬件未对齐访问异常或性能降级。

## 4.6 例外与登记（豁免白名单机制）

- 任何偏离 §4.2–§4.4 规范的结构体，必须显式登记在代码库的中央豁免表（`Engine/src/World/Scene/ComponentLayoutBudget.h`）；
- 豁免条目必须包含三项基本要素：**类型名称**、**架构论证理由**、**设定的到期复核日期**；
- **豁免是受控白名单，不是宽容度**：未在豁免表登记而超标的类型直接触发编译错误；超过复核期限的豁免条目在 ctest 门禁中产生警告，督促团队重审。

## 4.7 不需要本标准的场景（防御过度工程）

为了避免团队陷入无意义的微优化泥潭，以下场景**明确豁免**执行本标准：

1. **编辑器与离线工具**：WUI 面板代码、属性检查器、导入导出管线、开发期调试视窗；
2. **冷加载与初始化路径**：游戏启动配置解析、场景反序列化装载、关卡切换一次性初始化；
3. **低频对象**：整个游戏生命周期内全局实例总数 `≤ 100` 的逻辑实体；
4. **纯业务逻辑重构**：不涉及数据在内存中的存储排布、不改变 C1–C4 数据接口的逻辑流程重构；
5. **未经测量的性能直觉**：任何基于“我觉得这里对齐一下会更快”的猜想，严禁直接改动代码布局（可保留 `// PERF-HYPOTHESIS:` 注释并在任务台账中记录待测）。

## 4.8 成员顺序与填充（成员顺序是性能变量，不是风格问题）

**核心结论：成员顺序直接在底层硬件层面决定四项关键性能指标，因此属于架构标准强制管辖范围。**

### 四类物理影响面

| 影响面 | 物理硬件机制 | 实际性能后果 |
| --- | --- | --- |
| **M1 跨线拆分 (Cache Line Crossing)** | 热字段被前置冷字段推后，导致其内存地址横跨两条 64 字节 cache line 边界（`offset % 64 + size > 64`）。 | 每次访问该热字段必须触发两次 L1 数据缓存命中或两次独立的缓存行载入，使吞吐量减半。 |
| **M2 填充浪费 (Padding Bloat)** | 编译器遵循对齐规则自动在小尺寸字段后填充空洞（如 `bool, double, bool` 产生 24 字节，重排为 `double, bool, bool` 仅占 16 字节）。 | 增大连续数组的有效步长（stride），降低单条 cache line 内有效载荷密度，浪费内存带宽与容量。 |
| **M3 伪共享 (False Sharing)** | 多个并发线程各自高频写入**不同字段**，但这些字段碰巧分配在同一条 64 字节 cache line 内。 | 硬件缓存一致性协议（MESI）导致该 cache line 在不同 CPU 核心之间反复失效颠簸（ping-pong），多核吞吐严重暴跌。 |
| **M4 访问簇分离 (Access Cluster Dispersion)** | 在同一计算循环中总是被同时读取的字段被分散在不同 cache line，或高频写入字段与静态只读字段紧挨在一起。 | 打散访存局部性，增加所需缓存行总数；高频写入字段导致只读字段所在缓存行被反复置为脏行并强制同步。 |

### 可执行的成员顺序规则（R1–R6）

- **R1 热字段前置且不跨线（Hot Fields First & Contained）**  
  结构体的高频读写字段必须置于声明最前端，且必须保证：  
  $$\text{offsetof}(T, \text{HotField}) + \text{sizeof}(T::\text{HotField}) \le 64$$  
  确保所有核心热数据完全容纳在第一条 cache line 内。冷数据（元数据、统计、调试开关）统一放置在尾部或剥离至扩展结构。  
  *证据义务*：编写编译期断言锁定热字段偏移范围。

- **R2 零空洞优先（Zero Padding via Alignment Descending）**  
  POD 结构体内部成员默认按照字段的 `alignof` **严格降序排列**（8 字节对齐成员 → 4 字节 → 2 字节 → 1 字节），使 $\text{sizeof}(T)$ 精确等于各个成员大小之和。任何刻意保留的空洞必须附带架构解释。  
  *证据义务*：自动化门禁校验结构体大小与各成员大小累加值之差。  
  **冲突裁决（R1 vs R2）**：当降序排列（R2）会导致核心热字段被挤出第一条 cache line（违反 R1）时，**R1 具有绝对优先权**——访存局部性与缓存命中率优先于微小的空间紧凑性。

- **R3 伪共享物理隔离（False Sharing Physical Isolation）**  
  任何在多线程环境中可能被不同工作线程并发高频写入的变量，必须强制进行缓存行对齐隔离：  
  `alignas(64)` 且附加 `static_assert(sizeof(T) % 64 == 0)`；对于线程池局部计数器，必须采用 per-worker 槽位隔离设计。  
  **仓库实证案例**：`Engine/src/World/Core/Thread/JobSystem.cpp:20-37` 中，六个高频统计原子（`s_StatExecuted`、`s_StatStolen`、`s_StatExecutedWhileWaiting`、`s_StatOverflowPushes`、`s_StatQueueHighWater`、`s_StatWaits`）与每次 Kick/Complete 都会写入的 `s_PendingJobs` 混住在同一条 64 字节 cache line 内，导致所有工作线程发生全核乒乓颠簸（已列入 F7 修订）。  
  *证据义务*：并发写入变量必须登记在专属并发清单中，并包含行隔离编译期断言。

- **R4 访问簇紧密聚合（Access Cluster Packing）**  
  在同一热循环内被同时访问的字段，声明时必须物理相邻，以最大化空间局部性，使其尽可能容纳在最少数量的缓存行中。重排顺序必须引用调用点的访问模式作为依据。

- **R5 首成员即热入口（Hot Entrypoint at Offset Zero）**  
  结构体最常被解引用的核心入口字段应放置在偏移 0 处（`offsetof(T, Primary) == 0`）。使结构体首地址直接等价于热数据地址，节省基址加偏移的运算开销，并为指针别名与直接类型转换提供安全保障。

- **R6 顺序改动双向登记（Paired Registration of Reordering）**  
  结构体成员顺序的微调被正式定义为**结构布局破坏性改动**。改动后必须同步更新布局快照测试（门禁 A）与跨模块接口指纹（门禁 B）。严禁认为“总尺寸没变就可以随意调换顺序”。

### 一票否决补充条款

6. 将多线程高频并发写入的原子变量与其它普通状态字段混存在同一 64B 空间（严重违反 R3）。
7. 热数据访问成员偏移越过 64 字节分界线且无法提供基准收益证明（违反 R1）。
8. 为了消除局部几个字节的填充空洞而打乱成员，导致主计算字段溢出至第二条缓存行（违反 R1 > R2 优先级准则）。

### 反模式补充条款

- **细碎字段夹心**：在两个 8 字节对齐的热字段之间插入单字节 `bool` 或微小枚举，人为撕裂内存并制造空洞。
- **混合脏化缓存**：将多线程运行期的统计计数器（如 `TasksCompleted`）紧挨在只读配置结构体旁边，导致读取配置的核心不断受到写入核的缓存行作废惩罚。
- **平铺原子变量数组**：将每个 worker 线程的高频任务计数声明为连续数组 `std::atomic<uint64_t> counter[N];`（全部落入同一条缓存行疯狂冲突）。
- **无感重排**：在重构代码时仅因 IDE 格式化或个人美感随意重排字段，未验证对齐门禁。

## 5. 需要修复清单（正确性 / 防护缺口）

当前引擎中已识别的布局防护缺口与修复方案定义如下：

| 编号 | 问题描述 | 现状事实与证据 | 修复方案与工程手段 | 优先级 |

## 6. 需要优化清单（性能优化，基准驱动）

所有优化措施必须严格遵循“基准先行、数字背书、允许维持现状”的原则：

| 编号 | 优化课题 | 核心假设与潜在风险 | 判定标准与实施步骤 | 优先级 |
| --- | --- | --- | --- | --- |
| **O0** | **建立自动化微基准测试套件** | 缺少基准基础设施会导致所有布局与优化决策沦为空谈和主观猜测。 | 新建 `Tests/World/LayoutBenchmarks.cpp`（作为独立基准目标，**不纳入默认 ctest**，由维护脚本调用驱动）；度量输出各方案的 `ns/元素`、`cache lines/元素` 与内存分配次数，数据归档知识库。 | **P0** |
| **O1** | 热组件 48B 紧凑排布 vs 64B 填充 vs 分块 SoA 架构对比 | 顺序遍历时 48B 步长对应 0.75 条缓存行/元素，实际访存总带宽消耗优于 64B 步长（1.0 条/元素）；仅随机单实体访问存在跨行代价。 | 借助 O0 基准对比三类形态：(a) 现状 AoS 48B、(b) `alignas(64)` 对齐填充版、(c) 针对 SIMD 变换的局部分块 SoA；由实测数据决定选型，**完全允许维持现状**。 | **P1** |
| **O2** | `WorldTransformComponent`（64B 全矩阵）对场景根实体的冗余度分析 | 场景中大量根实体的全局变换直接等于局部变换，但作为物理与渲染的高频读取接口，若改为按需惰性计算可能将开销转移至更热的渲染收集循环。 | 通过基准统计项目中根实体所占比例及其读取频次；若收益明确则引入按需存储或稀疏池，若弊大于利则维持预先展平方案。 | **P1** |
| **O3** | 探索显式 SIMD / AVX2 批量计算路径 | 目前采用 glm 默认指令集，开启全仓 AVX2 属于重大的编译器全局开关改动，影响跨平台一致性。 | 测量 `TransformSystem::ComposeBatch` 占单帧时间的实际比重；仅当其耗时 `≥ 5%` 时，才针对性评估局域 AVX2 批量计算方案。 | **P2** |
| **O4** | 全局启用 `glm::mat4` 强制 16 字节对齐（`GLM_FORCE_ALIGNED_GENTYPES`） | 开启该宏将导致 `mat4` 对齐变为 16B，直接破坏所有内含矩阵组件的现存 `sizeof` 与字段偏移，引发连锁破坏。 | 仅在 O1 证明对齐矢量加载具备显著收益时才考虑局域采用；全局默认**保持关闭**，并在规范中确认为既定架构选择。 | **P2** |
| **O5** | 帧内高频结构体跨线与布局体检（`RenderExtract`、排序键、`SortedDrawItem`） | 瞬态高频提取结构体可能存在隐藏的跨缓存行开销。 | 结合门禁 C 的断言体系与 O0 基准，审计单帧遍历超万次的核心渲染中间结构，单项大于 64B 者列入优化候选。 | **P2** |
| **O6** | 线程池核心调度原子去伪共享验证 | 消除原子乒乓理论上可大幅提升高核心数下的作业窃取吞吐。 | 运行多线程高频 Kick / Complete 吞吐量基准，对比隔离前后的每秒任务完成数；有显著增益则采纳，无收益则保留现状避免内存膨胀。 | **P1** |
| **O7** | 核心组件成员顺序与访问簇体检（M1 / M4） | 历史代码中可能存在冷热字段混排导致的热字段跨行。 | 由门禁 A 输出所有核心组件的成员逐字段偏移热力分布，将所有导致核心读写字段落入第二缓存行的情形登记为优化议题。 | **P2** |

## 7. 门禁能力边界（抓得住 vs 抓不住）

本体系设计三组互相配合的自动化门禁，其防御边界界定如下（严禁夸大单组门禁的能力）：

| 门禁标识 | 覆盖范围与测试目标 | **抓得住（100% 拦截）** | **抓不住（需要其他手段兜底）** |
| --- | --- | --- | --- |
| **门禁 A**<br>`World.ComponentLayout` | 所有注册进 Schema 的组件 + 豁免表核对 | 1. 组件 `sizeof > 64B` 且未在豁免表登记；<br>2. 引入非平凡可拷贝成员（编译期 `MakeComponentStorage<T>` 直接报错）；<br>3. 组件尺寸发生变更而未同步基线快照。 | 1. 组件内部同尺寸字段重排（`sizeof` 不变且无字段级 offsetof 覆盖）；<br>2. 内部空洞浪费（未超过空洞上限）；<br>3. 未注册进 schema 的隐式逻辑组件（需由宏/手写断言兜底）。 |
| **门禁 B**<br>`World.RuntimeContract` | `Scene`、`WorldContext` 宿主 ↔ DLL 跨模块契约 | 1. 结构体总尺寸变化；<br>2. **关键成员等大小重排、位移、类型替换**（实测 `sizeof=1640` 不变，指纹从 `9904454385323809073` 突变为 `16225216100858202729`，直接红灯拦截）；<br>3. 跨模块 ABI 协议版本不一致。 | 1. 指纹采样清单之外的尾部私有指针成员顺序微调；<br>2. 虚函数表内部槽位顺序变动；<br>3. 单一模块内部私有数据结构重排。 |
| **门禁 C**<br>（编译期） | GPU 侧结构体（UBO / 实例缓冲 / 骨骼）、磁盘头与顶点 stride | 1. `ObjectUniforms`、`InstanceData`、`BoneUniforms`、`LightUniforms` 逐字段偏移漂移；<br>2. 顶点属性 stride / 偏移变动；<br>3. 资产头（`WModelIO` / `Mesh`）二进制布局错位。 | 1. 动态生成或着色器端自定义的 SSBO 布局；<br>2. CPU 端未在 C++ 显式建模声明的临时常量；<br>3. 不跨边界的内部局部渲染临时变量。 |

### A.2 非 Schema 运行期组件与已登记豁免实测值

- **`WorldTransformComponent`**：`64 字节`。满足单条 cache line 上限且为平凡可拷贝，通过编译期静态断言锁定。
- **`CameraViewComponent`**：`112 字节`。**已登记豁免**。内含 64B 投影矩阵与 32B 指纹参数；因每场景仅 1~2 台相机（Q1 = No），无热遍历性能顾虑。复核日期：2027-01-05。
- **`PhysicsInterpolationState`**：`68 字节`。**已登记豁免**。包含 64B 上一帧局部矩阵与有效位；作为 O2 优化候选，待基准测试裁决。复核日期：2026-11-05。
- **`HierarchyChildrenComponent`**：包含 `std::vector<Entity>`。**已登记豁免（有意非平凡）**。该组件为运行期反向子实体索引缓存，不入 `.wd`、不进属性面板、不走 schema 复制与预制体实例化，不设尺寸预算限制。

### A.3 门禁命令速查
